# Task: Scheduled email newsletters for Newsly

## Context
Newsly is a Next.js app (App Router) with Clerk auth, Prisma + Postgres, Inngest for background jobs,
and an existing news pipeline (SerpApi → dedupe → clustering → Firecrawl → AI evaluation → ranking → summary)
that runs from a `NewsRequest` row and writes `NewsStory` rows.

I want users to create **newsletters**: a saved set of the same news parameters as a `NewsRequest`
(everything except `date`), plus a schedule (daily / weekdays / weekly / monthly, send time, timezone),
delivered by email through **Resend**.

Users with identical parameters must **share one generated news set** ("edition") instead of running the
pipeline once per user. Someone who wants 5 stories gets the top 5 of the same ranked list someone else
gets 10 from. If a later send needs more stories than an edition has, generate only the extra ones.

I've attached reference implementations. Use them as the design, but adapt names, imports and folders
to this codebase:
- `newsletter.prisma` + `edition.prisma` — schema additions (Newsletter, NewsletterDelivery, NewsEdition, enums)
- `schedule.ts` — `computeNextRun()` and `newsWindow()` (Luxon, timezone/DST-safe)
- `fingerprint.ts` — `fingerprint()`, `periodKey()`, `normalizeParams()` for sharing editions
- `metros.ts` — city list used to normalise locations
- `newsletter.functions.ts` — Inngest scheduler, edition builder, per-newsletter send, failure handler

## Step 3 — Reuse the news pipeline (minimal changes)
- The pipeline must write `rank` (1 = most important) on every `NewsStory`.
- Let the pipeline function accept `{ requestId, count?, append? }`:
  - default (no `count`): behave exactly as today.
  - `append: true`: keep existing stories, add `count` more ranked after them, skipping URLs/clusters
    already stored. If the pipeline keeps the full ranked candidate list, take the next candidates
    instead of re-scraping.
- Make sure it can be awaited with `step.invoke` (it must return when stories are saved).
- Existing on-demand requests from the UI must keep working unchanged.

## Step 5 — Server side for the UI
Server actions or API routes (match the codebase), all requiring Clerk auth and checking ownership:
- create / update newsletter — validate with zod, reuse the news-request field validation;
  limits: storyCount 1–20, max 5 newsletters per user; `dayOfWeek` required for WEEKLY,
  `dayOfMonth` (1–31) for MONTHLY; validate timezone with `Intl`. Always set
  `nextRunAt = computeNextRun(...)` on create and whenever the schedule changes.
- pause / resume (resume recomputes `nextRunAt` from now), delete.
- "Send me a test now": sends one issue immediately (event to `newsletter/run` with a
  `scheduledFor` of now and a distinct id) without touching the schedule.
- list newsletters with their next send time and last 10 deliveries (status, story count, sent at).
- Unsubscribe route: `GET /unsubscribe?token=` and one-click `POST`, token = HMAC of newsletter id
  with `UNSUBSCRIBE_SECRET`; sets `isActive = false`; works without being signed in.

- Header: add a "Newsletters" link next to the existing nav items, active-state styled the same way,

## Constraints
- Don't change the behaviour of existing on-demand news requests.
- No duplicate emails: keep the conditional `nextRunAt` update, unique `(newsletterId, scheduledFor)`,
  Inngest event ids, and the Resend idempotency key from the reference.
- Never run the pipeline more than once per edition at a time (keep the concurrency key on the builder).
- Never send an empty email; mark the delivery SKIPPED instead.
- Keep secrets in env only.
